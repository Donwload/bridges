# 3D-спайк логики «Мосты»

Экспериментальный модуль: проверяем, что трёхмерный вариант головоломки
генерируется быстро и с ровно одним решением. Рендера здесь нет — только
математика. Существующая 2D-игра не затрагивается.

## Модель

- Остров — точка решётки `[x, y, z]`, ключ `"x,y,z"`.
- Мост идёт вдоль одной из трёх осей: у его концов совпадают две координаты.
- Кратность моста 1 или 2, число острова — сумма кратностей его мостов.
- Между парой островов на одной линии не должно быть других островов.
- Мосты вдоль разных осей пересекаются только внутри общей координатной
  плоскости (совпадает третья координата) — это обобщение креста из 2D.
- Требуется связность и единственность решения.

## Файлы

| Файл | Назначение |
| --- | --- |
| `spike.js` | Геометрия, солвер `Solver3D`, генератор `generateBoard3d`, расширение карты `expandBoard3d`, ГПСЧ `mulberry32`. |
| `generator.js` | `BridgesGenerator3D`: протокол запросов к генератору (`handleRequest`, `generateBoard`, `expandBoard`) и клиент с Worker и запасным синхронным путём. |
| `worker.js` | Тонкий classic-worker: `importScripts("spike.js", "generator.js")` и `onmessage` → `handleRequest`. |
| `game.js` | Состояние партии `BridgesLogic3D`: правила постановки моста, подсчёт, проверка победы, `boardSnapshot`, `applyExpansion`, `expandLevel`. |
| `bench.cjs` | Кросс-проверка солвера против перебора «в лоб» + бенчмарк генерации. |
| `explore.cjs` | Разведка «рабочего коридора»: размер поля и число островов. |

`spike.js` совместим и с браузером (классический script), и с Node
(`module.exports`).

## Как запускать

```powershell
node logic3d/bench.cjs
node logic3d/explore.cjs
node --test tests/logic3d.test.cjs       # 10 тестов 3D-логики и расширения
node --test tests/generator3d.test.cjs   # 12 тестов протокола и клиента Worker
node --test tests/logic.test.cjs         # 34 теста 2D-игры (не трогаются)
```

## Результаты

### Корректность

- Солвер `Solver3D` сверен с независимым перебором «в лоб» на **400 случайных
  картах — расхождений 0**.

Выводы:

- **Неудач нет нигде** — генератор с единственностью решения стабилен во всём
  диапазоне. Риск, ради которого делался спайк, снят.
- На кубе 3×3×3 при расстоянии ≥2 между островами помещается **не больше
  8 островов** (дальше просто нет свободных клеток), зато генерация < 1 мс.
- До ~10 островов время комфортное (единицы мс). На 12+ островах появляются
  редкие всплески до 150–800 мс — это уже чувствительно для главного потока.

### Рекомендуемый коридор

- **Демо/туториал:** 3×3×3, 6..8 островов — 0.4 мс, всегда уникально.
- **Основная игра:** 4×4×4, 7..10 островов — единицы мс.
- **Рост по уровням:** расширение карты после победы (см. ниже) — 3→5→7×7×7,
  дальше +2..4 острова внутрь.
- На 12+ островах/полях 5+ генерацию стоит уводить в **Web Worker**, иначе
  редкие всплески будут подмораживать интерфейс.

### Расширение карты после победы

`expandBoard3d(board, options)` — 3D-аналог `logic/expansion.js`. Старая карта
сдвигается в центр выросшего куба, а новые острова ставятся **листьями**:
у каждого ровно один видимый сосед, поэтому его мост вынужден, а число равно
кратности этого моста. После вычитания вынужденных мостов остаётся прежняя
карта, а она по инварианту игры единственна — солвер нужен только как
страховка, если структурная проверка не сошлась.

Чтобы новые острова не видели друг друга, **никакие два из них не должны
лежать на общей линии**. Поэтому у каждого нового острова уникальны все три
«ключевые пары» — `(y,z)`, `(x,z)` и `(x,y)`: это 3D-аналог уникальных строк
и столбцов в 2D. Первое предположение «достаточно уникальной пары `(x,y)`»
неверно: два острова с `x = 0` и одинаковым `z` попадают на одну линию по `y`.

Что ещё проверяется при постановке листа:

- клетка не занята и не лежит строго внутри существующего моста (иначе мост
  старого решения рассыпается на две части);
- новый мост не пересекается с уже существующими и намеченными;
- число соседа после прибавки не превышает 8;
- клетки внутри нового моста закрываются для следующих листьев.

Наружу возвращаются только **старые** мосты (со сдвигом): числа вырастают,
а достроить листья — дело игрока. Ровно как в 2D.

Замеры (`node --test tests/logic3d.test.cjs` — 8 карт × 3 расширения,
`Solver3D.countSolutions(2) === 1` на каждом шаге; плюс сквозной прогон в
браузере — 23 расширения подряд, 6 → 91 остров):

| Поле | Островов | Шаг расширения | Решений |
| --- | --- | --- | --- |
| 3×3×3 → 5×5×5 → 7×7×7 | 6 → 63 | 3..8 мс | 1 |
| 7×7×7 → 9×9×9 (тесно) | 63 → 91 | 8..80 мс | 1 |

Всплеск 80 мс — единственный: на 63 островах в 7×7×7 компактная постановка
не нашлась (40 попыток), и куб подрос до 9×9×9. Дальше шаги снова 7–9 мс.

### Генерация в Web Worker

Подбор поля и проверка единственности — самая дорогая часть игры: на 12+
островах одна попытка занимает десятки миллисекунд, а иногда 100–200 мс.
Раньше это происходило в главном потоке, и интерфейс подвисал на время
нажатия «Сложнее». Теперь тяжёлая часть уходит в отдельный поток.

Устройство:

- `generator.js` — чистые операции (`generateBoard`, `expandBoard`,
  `handleRequest`) и клиент `BridgesGenerator3D` с методами `generate`,
  `expand` и синхронными `generateSync`, `expandSync`.
- `worker.js` — classic worker без сборщика: `importScripts("spike.js",
  "generator.js")`, затем `onmessage` → `handleRequest`.
- Через границу потока едут только данные: вместо функции `rng` в запросе
  лежит `seed`, а `mulberry32` строится на стороне воркера. Это же делает
  генерацию воспроизводимой в тестах.

Протокол:

```
запрос:  { id, type: "generate", options }
         { id, type: "expand", board, options }
ответ:   { id, ok: true, result } | { id, ok: false, error }
```

Расширение карты уезжает в воркер **одним** запросом: вместе с планами
(обычный рост → рост за мягким пределом → один остров). Приём результата —
`BridgesLogic3D.applyExpansion`: проверка «карта решена» осталась в логике,
поэтому воркер не может сдвинуть непройденную партию.

Запасной путь обязателен и молчалив: если `Worker` недоступен (например,
`file://`), конструктор бросил исключение, воркер ответил `ok: false`,
не ответил за 5 с (`WORKER_TIMEOUT_MS`) или упал — поле считается синхронно
в текущем потоке. Игра работает всегда, просто на больших полях возможен
рывок. После падения воркер отключается, и следующие запросы идут сразу
синхронно.

В `Bridges3DApp` запросы нумеруются сквозным `requestSeq`: ответ устаревшего
запроса отбрасывается, поэтому быстрые клики «Сложнее»/«Проще» не дают
прыжка назад (побеждает последний). Повторное расширение во время уже
идущего игнорируется (`_expanding`).

Замеры в браузере (Chrome, поле 6×6×6 = 14–18 островов):

| Сценарий | Время | Тики таймера 4 мс | Макс. пауза потока |
| --- | --- | --- | --- |
| 8 полей подряд синхронно | 344 мс (мед. 34.9, макс 188.6) | 0 | — (поток занят целиком) |
| Те же 8 полей через Worker | 617 мс (0.002–0.2 с на поле) | 46 | 16 мс |
| Один `requestLevel(6)` через Worker | 14 мс | 2 | 5 мс |

Разброс по seed'ам большой (решение ищется с бюджетом по времени), поэтому
сравнивать надо не отдельные поля, а поведение потока: при синхронной
генерации таймеры не срабатывают ни разу, с воркером — идут всё время.
Накладные расходы сообщений на маленьких полях — медиана 1.5 мс, максимум
5.7 мс на запрос.

Гонки и отказы проверены в браузере: `requestLevel(4)` + сразу
`requestLevel(6)` → применяется только поле 6×6×6, статус и курсор
сбрасываются; двойной клик «Расширить карту» → ровно одно расширение;
расширение через воркер → уровень 2, поле 5×5×5, старые мосты на месте,
конфетти и баннер сброшены; воркер с битым `workerUrl` → `hasWorker: false`
и поле всё равно сгенерировано; консоль чистая, `gl.getError() === 0`.
